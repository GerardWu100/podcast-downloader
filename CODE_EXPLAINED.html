Podcast Downloader: reading the code

What the program does, how its parts connect, and which choices keep the MP3 library free of duplicates.

How to use this

Sections follow a download from settings through the queue, URL rules, expansion, age check, download, verification, tagging, publishing, cleanup, the browser interface, and the scheduler. Each snippet comes from the file named above it. Coloured boxes mark design choices and traps. The intended reader is new to this repository.

Snippets are verbatim, except that the two long command lists are shown two entries per line so they fit the page. Nothing else is reformatted or shortened without saying so.

The process in plain English

urls.txt lists YouTube channels, playlists, and individual videos. On schedule, the program turns each channel or playlist into video URLs, skips Shorts and videos that are too new, then gives the rest to yt-dlp. That program downloads the audio and converts it to MP3. For YouTube, SponsorBlock removes marked sponsor and self-promotion segments. The program writes a date and source link into each finished file's tags, moves it into a channel folder, and records its URL in a history file so it is not downloaded twice. A small web page lets you edit the source list.

Words used on this page

yt-dlp is the command-line program that talks to YouTube and downloads media; this project does not make HTTP requests to YouTube itself. ffmpeg and ffprobe convert and inspect audio files. SponsorBlock is a community database of timestamps for sponsor reads in YouTube videos. Audiobookshelf is the self-hosted audio library this project feeds. A file lock is an operating-system control that makes processes take turns using a file.

What each setting changes
SettingChange it and this happens
channel_countHow many recent videos are taken from each channel or playlist per run. For channels the program actually asks yt-dlp for six times this number, because Shorts and too-new uploads get filtered out before the target count is reached.
min_channel_video_age_hoursHow long a YouTube video must have existed before it is downloaded. The point is to give SponsorBlock contributors time to submit the sponsor timestamps. Set it to 0 to disable the wait entirely.
delay_secondsSleep between items in a run. Raising it makes a run gentler on YouTube and much slower.
retention_daysHow long a channel MP3 stays before being deleted, measured from the date the program wrote into the file's own tags. Playlist and one-off files are never deleted.
download_timeout_secondsWall-clock limit on one yt-dlp attempt, covering download plus MP3 conversion. Too low and long episodes fail forever, because a failed item is never recorded as done and so is retried on every future run.
always_use_cookiestrue: try YouTube with your browser cookies first, retry once without them. false: the other way round. Only YouTube ever sees cookies.
trust_x_forwarded_forWhether the web interface believes the client IP address that a reverse proxy claims. Only safe behind a proxy you control; see the limitations section.
output_dir, intermediate_dirFinished library folder and scratch folder. In Docker, PODCAST_DOWNLOAD_DIR and PODCAST_INTERMEDIATE_DIR override both, because downloads usually live on a different mount.
Why invalid settings stop the run

If you set channel_count = 0, the program reports the error instead of quietly using 1. The exception is a malformed true/false value, which uses the default. configparser already accepts yes, no, on, and off, so there is no useful third state.

02The queue file — QueueStore and the file locks

Two processes edit urls.txt: the downloader removes finished one-off videos, while the browser adds sources. Both use src/state/queue_store.py, and every read and write holds an operating-system file lock.

@contextmanager
def locked_text_file(path: Path, mode: str, lock_type: int) -> Iterator[TextIO]:
    """Open a text file and hold its process-shared ``fcntl`` lock."""
    path.parent.mkdir(parents=True, exist_ok=True)
    with path.open(mode, encoding="utf-8") as file_handle:
        fcntl.flock(file_handle.fileno(), lock_type)
        try:
            yield file_handle
        finally:
            # Publish buffered writes before another process can acquire the
            # lock and read this inode.
            try:
                file_handle.flush()
            finally:
                fcntl.flock(file_handle.fileno(), fcntl.LOCK_UN)
In plain words

The queue store is the only code that touches urls.txt. It adds URLs without duplicates, returns valid URLs, and removes a URL after its download finishes. Each operation holds a lock so the other process waits.

What it does

Input: a path to the queue file, plus a list of candidate URLs for append_urls. Output: append_urls returns how many lines were actually written; read_urls returns the valid URLs in file order; remove_url returns whether it found anything to remove. Role: the single owner of the queue file format, so no other module has to know that comments start with #.

  "https://www.youtube.com/@examplechannel",
  "javascript:alert(1)",

out — returned 1, and urls.txt became

https://www.youtube.com/@examplechannel
https://www.youtube.com/watch?v=dQw4w9WgXcQ

read_urls() ->

 'https://www.youtube.com/watch?v=dQw4w9WgXcQ']

Only one of four candidates was added: the short and watch links identify the same video, the channel was already present, and javascript: is not an HTTP address.

Then remove_url("https://www.youtube.com/watch?v=dQw4w9WgXcQ") returned True and left the comment and channel lines untouched. Comments are never removed.

Trap: the missing final newline

A hand-edited urls.txt may have no newline after its last line. Appending then would join the new URL to the old one. LockedLineFile checks the final byte before the first append and writes the missing newline. It reads one byte with os.pread, so it does not read an entire large file.

Why a lock instead of a database

The project's state should stay readable and editable in a text editor. A file lock adds safe updates without changing that. Without it, the downloader could read the file, the browser could append a URL, and the downloader could write its older copy back over the new URL.

03Reading a URL — media/urls.py and media/youtube.py

The two files have separate jobs. urls.py only checks whether a string is an HTTP address. youtube.py contains the YouTube-specific rules.

def normalize_youtube_url(url: str) -> str:
    """Normalize a YouTube video URL to the canonical watch format."""
    parsed = urlparse(url)
    hostname = (parsed.hostname or "").lower()
    # Empty parts drop the leading slash and any trailing slash in one step.
    path_parts = [part for part in parsed.path.split("/") if part]

    if hostname == "youtu.be":
        video_id = path_parts[0] if path_parts else ""
        return f"https://www.youtube.com/watch?v={video_id}" if video_id else url

    if hostname in {
        "www.youtube.com",
        "youtube.com",
        "m.youtube.com",
    }:
        if path_parts[:1] == ["watch"] and len(path_parts) == 1:
            query = parse_qs(parsed.query)
            video_id = query.get("v", [""])[0]
            return f"https://www.youtube.com/watch?v={video_id}" if video_id else url
        if path_parts[:1] == ["live"]:
            video_id = path_parts[1] if len(path_parts) > 1 else ""
            return f"https://www.youtube.com/watch?v={video_id}" if video_id else url

    return url
In plain words

YouTube can show one video at several addresses. This function rewrites them into one standard form so the program can recognise duplicates.

What it does

Input: any URL string. Output: a YouTube video in the standard watch?v=ID form, or the unchanged URL for anything else, including channels and playlists. Role: this defines URL identity for the system. The queue, one-shot bypass file, and download history compare normalized URLs, so an error here can download one episode twice.

The same run showed that is_channel_or_playlist is true for /@examplechannel, /@examplechannel/streams, /channel/UC..., and /playlist?list=.... It is false for watch?v=abc&list=PL123, which remains a video even when it appears in a playlist.

Why extra query parameters are removed

Share links can include tracking and position parameters such as ?si=, &t=42, and &list=. Keeping them would make the same episode look different when copied from different devices. Only the video identifier remains.

Trap: a similar-looking hostname

is_youtube_url compares the parsed hostname with an exact set. It does not accept any host that merely ends with youtube.com. Therefore https://notyoutube.com/watch?v=abc123 stays an ordinary direct link and never receives your cookies. A test covers this case.

04Turning a channel into videos — expand_channel_or_playlist()

A channel URL is not a video to download. The project first asks yt-dlp for a list of video URLs without downloading them.

def _build_expansion_command(url_clean, channel_count, cookies_file, *, full_playlist=False):
    is_channel = _is_channel_url(url_clean)
    expansion_url = _channel_tab_expansion_url(url_clean) if is_channel else url_clean
    fetch_count = channel_count * 6 if is_channel else channel_count
    command = [
        "yt-dlp",
        "--flat-playlist",
        "--extractor-args", "youtubetab:approximate_date",
        "--sleep-requests", "0.5",
        "--print", "%(url)s\t%(timestamp)s\t%(upload_date)s",
    ]
    if cookies_file:
        command.extend(["--cookies", str(cookies_file)])
    if not (full_playlist and not is_channel):
        command.extend(["--playlist-end", str(fetch_count)])
    command.extend(["--", expansion_url])
    return command
In plain words

Ask yt-dlp for recent videos and upload dates, one per line. Remove Shorts and videos that are too new, then keep the first few that remain.

What it does

Input: a channel or playlist URL, the requested count, the minimum age, and the cookie policy. Output: an ordered list of video URLs, or an empty list if both attempts fail. Role: the one place that turns a monitored source into download items.

No --playlist-end at all, so the whole playlist is listed. That mode is only reachable from the "run now" checkbox in the browser page.

The same run chose these channel tabs: /@examplechannel became /@examplechannel/videos; /streams stayed unchanged; /@examplechannel/shorts became /videos; and /channel/UC.../videos stayed unchanged.

Why it asks for six times the requested count

The setting is the number of episodes to keep, not the number of rows YouTube should return. Shorts and videos from the last day are removed after the list arrives. Asking for twelve when the target is two gives the filter enough candidates, while --flat-playlist still uses one listing request instead of opening every video.

Why a bare channel URL becomes the videos tab

A bare channel address can mix uploads, Shorts, and livestreams, depending on YouTube's layout. Using /videos makes the result predictable. Anyone who wants livestreams can write /streams in urls.txt.

Trap: the retry only changes cookies

After a failed first attempt, the code tries once more with the opposite cookie choice. It does not retry the same settings, wait before retrying, or make a third attempt. A temporary network failure skips the channel this run; the next scheduled run tries it again. This suits a program that runs every other day, but there is no general network-retry logic.

05The waiting period — is_old_enough()

A new YouTube video may not have SponsorBlock data yet. The program waits before downloading it so sponsor reads can be marked.

def is_old_enough(timestamp_raw, upload_date, min_channel_video_age_hours) -> bool | None:
    """True if old enough, False if too new, None if age is unknown."""
    if min_channel_video_age_hours <= 0:
        return True

    if _metadata_value_is_present(timestamp_raw):
        try:
            timestamp = int(timestamp_raw)
            age_seconds = datetime.now(timezone.utc).timestamp() - timestamp
            return age_seconds >= min_channel_video_age_hours * 3600
        except ValueError:
            pass

    if _metadata_value_is_present(upload_date):
        try:
            upload_day = datetime.strptime(upload_date, "%Y%m%d").date()
            next_day_start = datetime.combine(
                upload_day + timedelta(days=1), datetime.min.time(), tzinfo=timezone.utc)
            allowed_at = next_day_start + timedelta(hours=min_channel_video_age_hours)
            return datetime.now(timezone.utc) >= allowed_at
        except ValueError:
            return None

    return None
The formula

When yt-dlp gives the exact publication time $t_{\text{pub}}$ in seconds since 1970, the test is

$$t_{\text{now}} - t_{\text{pub}} \ \ge\ 3600\,h_{\min}$$

When only a YYYYMMDD date is available, the exact time is unknown. The code assumes the video was published at the end of that day and starts the wait at midnight after it:

$$t_{\text{now}} \ \ge\ \text{midnight}(d_{\text{upload}} + 1\ \text{day}) + 3600\,h_{\min}$$

$t_{\text{now}}$ is the current time in seconds; $t_{\text{pub}}$ is the publication time in seconds; $h_{\min}$ is min_channel_video_age_hours (24 by default); $d_{\text{upload}}$ is the upload date; and all times use Coordinated Universal Time (UTC).

What it does

Input: the timestamp and upload-date text from yt-dlp, plus the configured minimum age. Output: True, False, or None. Role: three possible answers. None means the age is unknown, and every caller allows the download.

Sample data
in and out — is_old_enough(timestamp, upload_date, 24) 
timestamp 2 hours old                timestamp='1786395218'   upload_date=''           -> False
timestamp 30 hours old               timestamp='1786294418'   upload_date=''           -> True
no timestamp, upload_date today      timestamp='NA'           upload_date='20260810'   -> False
no timestamp, upload_date 2024-01-05 timestamp='NA'           upload_date='20240105'   -> True
both missing                         timestamp='NA'           upload_date='NA'         -> None
garbage upload_date                  timestamp='NA'           upload_date='not-a-date' -> None   <- unknown, not blocked

For the second row, the run happened at Unix time 1786402418. The age is 1786402418 minus 1786294418 = 108000 seconds, or 30 hours. Since 30 is at least 24, the result is True.

Why unknown allows the download

yt-dlp writes NA when a field is missing, and channel listings often omit exact times. If unknown meant "wait", a channel without dates would never download anything, with no clear error. Allowing an unknown age may leave a sponsor read in one episode, which is the smaller risk here.

Trap: date-only metadata creates a longer wait

With the default 24 hours and only an upload date, a video published at 01:00 UTC waits until 00:00 the next day plus 24 hours: 47 hours, not 24. This is deliberate caution when the publication time is unknown, so the setting is a minimum, not the exact delay.

The one-shot override

Choosing "run now" in the browser or passing --skip-age-check on the command line writes the video URL to bypass_age_check_urls.txt. BypassStore.consume() removes the line and reports the match in one locked read-modify-write before the download starts. A failed download does not preserve permission for a later run; the override is used once.

06Running the downloader — YtDlpClient

src/downloads/ytdlp_client.py has four jobs: build the command, run it with a time limit, decide whether to retry with another cookie choice, and report the result.

def build_download_command(self, url: str, work_dir: Path, cookies_file: Path | None) -> list[str]:
    """Build one audio-download command with a safe URL separator."""
    command = [
        "yt-dlp",
        "--paths", f"temp:{work_dir}",
        "--extract-audio",
        "--audio-format", "mp3",
        "--audio-quality", "0",
        "--no-mtime",
        "--embed-thumbnail",
        "--add-metadata",
        "--output", str(work_dir / YTDLP_OUTPUT_FILENAME_TEMPLATE),
    ]
    if is_youtube_url(url):
        command.extend(["--sponsorblock-remove", SPONSORBLOCK_CATEGORIES])
    else:
        command.append("--no-playlist")
    if cookies_file is not None:
        command.extend(["--cookies", str(cookies_file)])

    # `--` keeps a user-supplied URL beginning with `-` from becoming an
    # option to yt-dlp.
    command.extend(["--", url])
    return command
In plain words

Build the command, run it, and retry once with the opposite cookie choice if needed.

What it does

Input: a direct media URL and its scratch folder. Output: a YtDlpResult containing the exit status, command output, changed MP3 files, before and after snapshots, and the number of attempts. Role: the only code that runs the external downloader, so the download logic can be tested without a network.

There is no SponsorBlock and no cookies. SponsorBlock has YouTube data only, and private cookies must not be sent to an unrelated site.

Why every command ends with two hyphens

URLs in urls.txt and the web form are user input. A URL beginning with a hyphen could be read by yt-dlp as an option. Putting -- before the URL tells the argument parser that everything after it is a value. The command is also passed as a list, not a shell string, so shell injection is not possible.

Why cookie order is configurable

Cookies make YouTube treat a request as signed in, which can get past "confirm you are not a bot". A stale or over-used cookie file can also cause failures that an anonymous request would avoid. The project lets you choose which option comes first, then tries the other once. Both directions use the same two-attempt path.

07Proving the download worked — file snapshots

The downloader checks the files, not only the exit code.

def snapshot_audio(self, work_dir: Path) -> AudioSnapshot:
    """Capture recursive MP3 modification time and size state."""
    captured_files: dict[Path, tuple[int, int]] = {}
    for audio_file in work_dir.rglob("*.mp3"):
        if not audio_file.is_file():
            continue
        file_stat = audio_file.stat()
        captured_files[audio_file] = (file_stat.st_mtime_ns, file_stat.st_size)
    return AudioSnapshot(files=captured_files)

@staticmethod
def changed_audio_files(before_snapshot, after_snapshot) -> list[Path]:
    """Return MP3 paths created or changed between two snapshots."""
    return sorted(
        audio_file
        for audio_file, after_state in after_snapshot.files.items()
        if before_snapshot.files.get(audio_file) != after_state
    )
In plain words

yt-dlp can return success without producing an MP3. The program lists MP3 files in the scratch folder before and after the attempt, and counts the download as successful only if a file appeared or changed.

The formula

Let $B$ be the set of MP3 files in the scratch folder before the attempt and $A$ the set after, and let $s(p)$ be the state of file $p$, meaning the pair (modification time in nanoseconds, size in bytes). A file $p \in A$ counts as changed when

$$p \notin B \quad\text{or}\quad s_A(p) \ne s_B(p)$$

The attempt succeeds only when at least one such $p$ exists.

Both sets cover only this source's scratch folder. A file created by another source or process cannot prove that this URL worked.

Sample data
in — two snapshots 
before: {'/w/old.mp3': (1000, 500)}
after : {'/w/old.mp3': (1000, 500),
         '/w/new.mp3': (2000, 900)}
out — changed_audio_files() 
[PosixPath('/w/new.mp3')]

with an unchanged folder:
[]                        <- treated as a failed attempt

An empty result triggers the second attempt with the other cookie choice, even when yt-dlp returned exit code zero.

Why size and modification time instead of a checksum

These files are tens of megabytes, and the comparison happens twice per download. A checksum would read every byte. The question is whether this run wrote anything, which a nanosecond timestamp and byte count answer with one stat call per file.

Trap: recovery accepts only one MP3

If nothing changed, _find_recoverable_existing_audio continues only when the scratch folder contains exactly one MP3. This handles a previous run that downloaded the file but crashed while writing tags; the next yt-dlp attempt then says "already downloaded" and changes nothing. It is still a guess, and the limitations section shows when it can choose the wrong file.

08Tagging the MP3 — AudioMetadataWriter

Audiobookshelf reads an episode's date from tags inside the audio file, not from the file's timestamp on disk. After a successful download, the project writes its own tags.

command = [
    "ffmpeg", "-y",
    "-i", str(audio_file),

# Copy the result back to the same path so library scanners keep

In plain words

Rewrite the tags with ffmpeg without re-encoding the audio, then copy the result back into the original file. The library scanner keeps seeing the same file.

What it does

Input: an MP3 path, the completion timestamp as text, the source URL, and optionally a readable channel name. Output: nothing on success; a RuntimeError if ffmpeg fails. Role: it sets the date and podcast name shown by Audiobookshelf and records the source video URL.

Why the bytes are copied back

Audiobookshelf's scanner and file watcher identify files by path and inode number, the operating system's identifier for a file. Replacing the original with a renamed temporary file would create a new inode, so the library could treat it as a delete and a new file and lose the listen position. Copying into the existing file keeps the inode.

Why the date is download time

The podcast app should show new arrivals in the order received. A channel backfilling a five-year-old episode would otherwise place it far back in the list. Retention reads the same tag, so "keep for 30 days" means 30 days since download.

Trap: the temporary file must not end in .mp3

The temporary file is named .<original name>.download-date.tmp. If it ended in .mp3, the next snapshot_audio call would count it as a changed audio file and publish it as a duplicate. The leading dot also hides it from most file browsers.

    decoded_name = unquote(raw_name).strip()
    decoded_name = decoded_name.removeprefix("@")

Why there are two folders, scratch and library

intermediate_dir holds partial downloads, thumbnails, the intermediate audio stream, and the temporary tagging file. Only a finished, tagged MP3 moves to output_dir. Audiobookshelf watches output_dir, so it does not see fragments. If both paths point to the same folder, the code detects that and deletes non-MP3 leftovers in place instead of moving files.

Why failure deletes the whole scratch folder

Every failure path calls _finalize_intermediate_cleanup(work_dir), which removes the source's scratch folder. A failed item is not added to the history file, so the next run starts it again. Removing fragments keeps the next before-and-after snapshot clear.

The two locks around a download

Channel and playlist items use archive_store.locked_download_claim(), which locks a small separate file. The history file is locked only for its short read or append. A download can take an hour; holding the history lock that long would block the browser's duplicate check. One-off videos use .direct-download.lock in the scratch folder because they share the singles workspace.

Trap: history is written only after success

downloaded_urls.txt gets a line only after the MP3 is tagged and published. A failed download is therefore retried automatically. A video that always exceeds download_timeout_seconds is retried forever because it is never recorded as complete.

10Deleting old episodes — retention

In plain words

Before a full run, the program scans monitored YouTube channel folders, reads each MP3's stored date, and deletes files older than the retention window. It also removes each deleted video's URL from the history so it can be downloaded again.

The formula

An MP3 at path $p$ is deleted only when all four conditions hold:

$$p \in D_{\text{channel}}, \quad d(p) \ \text{is readable}, \quad u(p) \ \text{is readable}, \quad d(p) < t_{\text{now}} - R$$

$D_{\text{channel}}$ is the set of output folders for YouTube channels currently in urls.txt; $d(p)$ is the download date in the file's date tag; $u(p)$ is the source URL in its comment tag; $t_{\text{now}}$ is the current Toronto time; and $R$ is retention_days, 30 by default.

Why all four conditions are required

Each condition prevents a different mistaken deletion. Limiting cleanup to current channel folders protects playlists and one-off downloads. Requiring a readable date protects files copied in by hand. Requiring the source URL lets the program remove the matching line from downloaded_urls.txt; otherwise the file would disappear while remaining marked as downloaded. Every skipped file is logged with its reason.

Trap: retention runs before the history check

In download_all, cleanup runs first. If it ran later, the history check would skip a video, then cleanup would delete its file and history line. The video would not be eligible again until the next run. Running cleanup first makes it eligible in the same pass.

How sign-in works

What it does

Input: a username, password, and one-time token from the form. Output: a random session identifier in a cookie and .ui_sessions.json. Role: the gate for every queue edit.

Passwords are never stored. src/passwords.py uses PBKDF2-HMAC-SHA256 (Password-Based Key Derivation Function 2; HMAC means Hash-based Message Authentication Code, and SHA means Secure Hash Algorithm), a deliberately slow password-hashing method. It uses 600,000 iterations and a random 16-byte salt, then stores pbkdf2_sha256$iterations$salt$hash. At start-up, src/credentials.py reads passwords from .env, checks them against the stored hashes, and re-hashes only when a password changes.

Sample data
in and out — hash_password() then verify_password() 
hash_password("correct horse battery staple")
  -> 'pbkdf2_sha256$600000$_WfqIBCT9slw60mLrRyiUw$mNHi8im1JustYipg8g-gR7D2eLfJvg4vIFe9kZp9EKg'

verify_password("correct horse battery staple", stored)  -> True
verify_password("wrong", stored)                          -> False
verify_password("x", "not-a-hash")                        -> False

The stored value includes its iteration count and salt, so the verifier reads them from the string. verify_password rejects counts outside 100,000 to 1,000,000, preventing a tampered file from demanding unlimited processor time during sign-in.

Why an unknown username takes as long as a wrong password

If the code skipped hashing for an unknown name, sign-in would be faster for an invalid name than for a valid name with a wrong password. An attacker could use that timing difference to find account names. When no name matches, the code hashes the submitted password against the first stored hash as a decoy. It also uses secrets.compare_digest to compare names in constant time.

The ban rule

Five failed attempts from one client address within a rolling ten-minute window create a fifteen-minute ban in .login_state.json. A failure after the window starts a new count. The ban is checked before password hashing, so a banned address cannot use the server's processor time.

Trap: form tokens are required and login tokens are single-use

Cross-Site Request Forgery (CSRF) is when another website makes your signed-in browser submit a form here. Each page includes a random token that the server remembers, and each form must send it back. The sign-in token is removed as soon as it is used and expires after ten minutes, so a captured form cannot be replayed.

Why /logs returns 401 instead of redirecting

The queue page asks /logs for updates every fifteen seconds. If the session expired, a redirect would be followed by fetch, which would receive the sign-in page and display it as log text. Status code 401 means "not authenticated", so the script can handle the expired session correctly.

Response headers on every page

auth.py sets a Content Security Policy (CSP) of default-src 'none' with a random per-request nonce for the inline script. It also sets frame-ancestors 'none', X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: same-origin, and Cache-Control: no-store. In plain terms, the page cannot load from another site, appear inside another site's frame, or be cached.

12The scheduler — start.py and trigger.py

Inside Docker, one process serves the web page and runs the schedule. start.py keeps the web server in the main thread and runs the scheduler in a background thread.

In plain words

At 06:00 every other day, update yt-dlp, wait five minutes, and run the full queue in a separate process. If the browser adds a URL meanwhile, wake early and handle only that URL. The Run button on the queue page asks for the whole-queue pass by hand.

What it does

Input: scheduled_run_hour and scheduled_run_interval_days from config.ini, YT_DLP_AUTO_UPDATE, and wake-up requests from the browser. Output: child processes running python -m src.cli, with no arguments for a full run or with --download-single-url or --download-full-playlist for an immediate run. Role: the only code that decides when downloads happen.

Why the downloader is a separate process

A crash or memory leak while handling yt-dlp takes down a short-lived child, not the web server. Each child also starts with a clean logging setup and working directory. The two processes share state through locked files, which is why src/state/ exists.

Why the run time comes from the calendar

The old scheduler slept 48 hours after each run, so the run time drifted with every restart and every redeploy. src/schedule.py instead asks the date: a day is a run day when its day count since year 1 divides evenly by the interval, and the run starts at the configured hour on that day. Nothing about the answer depends on when the process started, so the web page and the scheduler agree on the next run without sharing any state. A container that was down at the scheduled hour catches up once when it comes back, then returns to the fixed times.

Why the browser passes the URL

trigger.py keeps two lock-protected lists: one for single videos and one for full playlists. If the browser sent only a wake-up signal, the scheduler would process the whole queue, including every channel, for one pasted link. Passing the URL limits the immediate run to that item.

Trap: adding a channel does not start a run

Only direct videos and explicitly selected playlists trigger an immediate run. A new channel waits for the next scheduled run, up to two days away, unless you press Run queue now. This avoids the expensive channel-expansion path, but the browser page does not show that the channel is waiting.

One defect found and fixed — src/media/youtube.py

The bug. normalize_youtube_url used parsed.path.lstrip("/") to build the video identifier. That removes a leading slash but not a trailing one, so https://youtu.be/dQw4w9WgXcQ/ became https://www.youtube.com/watch?v=dQw4w9WgXcQ/. What was examined and deliberately left alone

The remaining issues need design decisions, so they are documented below.

FLimitations, stated honestly

Retagging can destroy an MP3 when the disk fills

AudioMetadataWriter opens the finished MP3 for writing, truncating it to zero bytes, then copies the retagged bytes from a temporary file. If the copy fails, the original is gone and the finally block deletes the only complete copy. The caller then preserves the truncated MP3 for a later retry, and the one-file recovery rule can publish it. Keeping Audiobookshelf's inode stable conflicts with protecting the original file, so this needs a design decision.

The one-file recovery rule can choose the wrong MP3

_find_recoverable_existing_audio accepts any single MP3 in the scratch folder when a run changes nothing. If video A failed during tagging and video B's yt-dlp attempt then produces no file, A's audio is tagged with B's source URL, published, and B is recorded as downloaded. A stricter rule could require the filename to contain the video identifier that yt-dlp puts in square brackets, but that would not work for non-YouTube sources.

Channel folder names are not stable

For a /channel/UC... source, a live yt-dlp lookup supplies the readable folder name on every run. There is no cache. One network failure sends that run's downloads to the raw identifier, and retention then sees only one of the two folders. Sources written as /@handle are unaffected because their names come from the URL.

Everything depends on parsing yt-dlp's output

Channel expansion reads tab-separated lines from yt-dlp --print, and the age check treats NA as "missing". These are conventions of a tool that changes often to follow YouTube. If either changes upstream, the program may quietly produce zero videos instead of raising an error.

One shared account list, one process

Sign-in uses a small shared account list from .env, not separate user identities. Active sessions live in one process's memory. More than one web worker would break sign-in because each worker would keep a separate session map. The README describes this as a personal tool, not a multi-user service.

The shipped settings trust proxy headers

trust_x_forwarded_for = true is in config.ini, while the code default is false. This matches the supplied Docker Compose file, which binds the port to 127.0.0.1 behind a reverse proxy. If the port is exposed directly, a client can claim any address in an X-Forwarded-For header and evade the per-address sign-in ban. The setting is documented in the file and README, but it remains the sharpest configuration risk.

The detailed log rotates across processes

download.log uses a rotating handler with a five-megabyte limit and three backups. Each downloader run is a separate process. If two overlap, such as a manual run during the scheduled run, one process can rotate the log and drop entries from the other. The download is unaffected, but the log is incomplete under concurrency.
