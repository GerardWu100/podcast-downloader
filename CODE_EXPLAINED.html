Podcast Downloader: reading the code

What this program does, how its pieces fit together, and the handful of decisions that make the difference between a clean MP3 library and a pile of duplicates.

How to use this

Sections follow the order in which a download actually happens: settings, queue, URL rules, expansion, the age gate, the external download, proof of success, tagging, publishing, cleanup, then the browser interface and the scheduler that drives it all. Every code snippet is copied from the file named above it. Coloured boxes flag design choices and traps. The page is aimed at someone who has never opened this repository.

Snippets are verbatim, with one exception: in the two command-building functions, the long lists of flag-and-value pairs are shown two per line so they fit the page. Nothing else is reformatted and nothing is abridged without saying so.

The process in plain English

You keep a plain text file, urls.txt, holding YouTube channels, YouTube playlists, and one-off video links. On a schedule, the program turns each channel or playlist into a list of individual videos, skips the ones that are too new or are Shorts, and hands the rest to yt-dlp, which downloads the audio and converts it to MP3. For YouTube it also asks SponsorBlock to cut out sponsor and self-promotion segments. Each finished MP3 gets a date and a source link written into its tags, is moved into a folder named after the channel, and its URL is written to a history file so it is never fetched twice. A small web page lets you add and remove sources from a browser.

Words used on this page

yt-dlp is the external command-line program that actually talks to YouTube and downloads media; this project never speaks HTTP to YouTube itself. ffmpeg and ffprobe are the external audio tools that convert and inspect files. SponsorBlock is a community database of timestamps marking sponsor reads inside YouTube videos. Audiobookshelf is the self-hosted audio library this project feeds. A file lock is an operating-system marker that makes two processes take turns on the same file instead of overwriting each other.

What each setting changes
SettingChange it and this happens
channel_countHow many recent videos are taken from each channel or playlist per run. For channels the program actually asks yt-dlp for six times this number, because Shorts and too-new uploads get filtered out before the target count is reached.
min_channel_video_age_hoursHow long a YouTube video must have existed before it is downloaded. The point is to give SponsorBlock contributors time to submit the sponsor timestamps. Set it to 0 to disable the wait entirely.
delay_secondsSleep between items in a run. Raising it makes a run gentler on YouTube and much slower.
retention_daysHow long a channel MP3 stays before being deleted, measured from the date the program wrote into the file's own tags. Playlist and one-off files are never deleted.
download_timeout_secondsWall-clock limit on one yt-dlp attempt, covering download plus MP3 conversion. Too low and long episodes fail forever, because a failed item is never recorded as done and so is retried on every future run.
always_use_cookiestrue: try YouTube with your browser cookies first, retry once without them. false: the other way round. Only YouTube ever sees cookies.
trust_x_forwarded_forWhether the web interface believes the client IP address that a reverse proxy claims. Only safe behind a proxy you control; see the limitations section.
output_dir, intermediate_dirFinished library folder and scratch folder. In Docker, PODCAST_DOWNLOAD_DIR and PODCAST_INTERMEDIATE_DIR override both, because downloads usually live on a different mount.
Why the checks reject rather than clamp

A silently clamped setting is a setting that lies to its operator. If you write channel_count = 0, the program stops and tells you, instead of quietly behaving as if you had written 1. The one exception is a malformed true/false value, which falls back to the default, because configparser already accepts yes, no, on and off and there is no useful third state.

02The queue file — QueueStore and the file locks

Two processes edit urls.txt: the downloader removes finished one-off videos, and the browser page adds new sources. Both go through src/state/queue_store.py, and every read and write holds an operating-system file lock.

@contextmanager
def locked_text_file(path: Path, mode: str, lock_type: int) -> Iterator[TextIO]:
    """Open a text file and hold its process-shared ``fcntl`` lock."""
    path.parent.mkdir(parents=True, exist_ok=True)
    with path.open(mode, encoding="utf-8") as file_handle:
        fcntl.flock(file_handle.fileno(), lock_type)
        try:
            yield file_handle
        finally:
            # Publish buffered writes before another process can acquire the
            # lock and read this inode.
            try:
                file_handle.flush()
            finally:
                fcntl.flock(file_handle.fileno(), fcntl.LOCK_UN)
In plain words

The queue store is the only code allowed to touch urls.txt. It adds URLs without creating duplicates, reads out the valid ones, and removes one when its download finishes — each time holding a lock so the other process has to wait its turn.

What it does

Input: a path to the queue file, plus a list of candidate URLs for append_urls. Output: append_urls returns how many lines were actually written; read_urls returns the valid URLs in file order; remove_url returns whether it found anything to remove. Role: the single owner of the queue file format, so no other module has to know that comments start with #.

Sample data
in — urls.txt, plus four candidates 
# my sources
https://www.youtube.com/@examplechannel

append_urls([
  "https://youtu.be/dQw4w9WgXcQ",
  "https://www.youtube.com/watch?v=dQw4w9WgXcQ",
  "https://www.youtube.com/@examplechannel",
  "javascript:alert(1)",
])
out — returned 1, and urls.txt became 
# my sources
https://www.youtube.com/@examplechannel
https://www.youtube.com/watch?v=dQw4w9WgXcQ

read_urls() ->
['https://www.youtube.com/@examplechannel',
 'https://www.youtube.com/watch?v=dQw4w9WgXcQ']

Only one line was added from four candidates: the short link and the watch link are the same video, the channel was already listed, and the javascript: string is not an http address.

Then remove_url("https://www.youtube.com/watch?v=dQw4w9WgXcQ") returned True and left the comment line and the channel line untouched. Comments are never rewritten away.

Trap: the missing final newline

An operator who edits urls.txt by hand can leave the last line without a newline at the end. Appending straight to that file would glue the new URL onto the end of the old one and destroy both entries. LockedLineFile checks the file's final byte before its first append and writes the missing newline first. It reads exactly one byte with os.pread, so appending to a log with thousands of lines does not mean reading the whole file.

Why a lock and not a database

The whole point of this project is that its state is readable and editable with a text editor. A file lock buys the safety of a transaction without giving that up. Without it, the sequence "downloader reads, browser appends, downloader writes its older copy back" silently loses the newly added URL.

03Reading a URL — media/urls.py and media/youtube.py

Two files, deliberately separate. urls.py knows nothing about YouTube; it only answers "is this an http address at all". youtube.py holds every YouTube-specific rule.

def normalize_youtube_url(url: str) -> str:
    """Normalize a YouTube video URL to the canonical watch format."""
    parsed = urlparse(url)
    hostname = (parsed.hostname or "").lower()
    # Empty parts drop the leading slash and any trailing slash in one step.
    path_parts = [part for part in parsed.path.split("/") if part]

    if hostname == "youtu.be":
        video_id = path_parts[0] if path_parts else ""
        return f"https://www.youtube.com/watch?v={video_id}" if video_id else url

    if hostname in {
        "www.youtube.com",
        "youtube.com",
        "m.youtube.com",
    }:
        if path_parts[:1] == ["watch"] and len(path_parts) == 1:
            query = parse_qs(parsed.query)
            video_id = query.get("v", [""])[0]
            return f"https://www.youtube.com/watch?v={video_id}" if video_id else url
        if path_parts[:1] == ["live"]:
            video_id = path_parts[1] if len(path_parts) > 1 else ""
            return f"https://www.youtube.com/watch?v={video_id}" if video_id else url

    return url
In plain words

YouTube shows you the same video through several different addresses. This function rewrites all of them into one canonical form so the program can tell whether two links are really the same video.

What it does

Input: any URL string. Output: the canonical watch?v=ID form for a YouTube video, or the URL unchanged for anything else, including channels and playlists. Role: this is the identity function for the whole system. The queue, the one-shot bypass file and the downloaded history all compare normalized URLs, so if this function gets it wrong, the same episode is downloaded twice.

'https://youtu.be/dQw4w9WgXcQ'                               -> 'https://www.youtube.com/watch?v=dQw4w9WgXcQ'
'https://youtu.be/dQw4w9WgXcQ/'                              -> 'https://www.youtube.com/watch?v=dQw4w9WgXcQ'   <- fixed on this pass
'https://youtu.be/dQw4w9WgXcQ?si=abcdef'                     -> 'https://www.youtube.com/watch?v=dQw4w9WgXcQ'
'https://www.youtube.com/live/jNQXAC9IVRw'                   -> 'https://www.youtube.com/watch?v=jNQXAC9IVRw'
'https://m.youtube.com/watch?v=jNQXAC9IVRw'                  -> 'https://www.youtube.com/watch?v=jNQXAC9IVRw'
'https://www.youtube.com/@examplechannel'                    -> unchanged (a channel, not a video)
'https://www.youtube.com/playlist?list=PLrAX...'             -> unchanged (a playlist)
'https://videos.example.com/watch/episode-1'                 -> unchanged (not YouTube)

Classification, from the same run: is_channel_or_playlist is true for /@examplechannel, /@examplechannel/streams, /channel/UC... and /playlist?list=..., and false for watch?v=abc&list=PL123 — a video that merely happens to be inside a playlist is treated as one video, not as a playlist.

Why the query string is thrown away

Share links carry tracking and position parameters: ?si=, &t=42, &list=. Keeping them would mean the same episode pasted from a phone and from a desktop looked like two different episodes. Only the video identifier survives.

Trap: a lookalike hostname

is_youtube_url compares the parsed hostname against an exact set. It does not check whether the host merely ends with youtube.com, which is why https://notyoutube.com/watch?v=abc123 is correctly treated as an ordinary direct link and never gets your cookies attached. There is a test for exactly this.

04Turning a channel into videos — expand_channel_or_playlist()

A channel URL is not something you can download. It has to be turned into a list of individual video URLs first, and this project does that by asking yt-dlp to print a list rather than download anything.

def _build_expansion_command(url_clean, channel_count, cookies_file, *, full_playlist=False):
    is_channel = _is_channel_url(url_clean)
    expansion_url = _channel_tab_expansion_url(url_clean) if is_channel else url_clean
    fetch_count = channel_count * 6 if is_channel else channel_count
    command = [
        "yt-dlp",
        "--flat-playlist",
        "--extractor-args", "youtubetab:approximate_date",
        "--sleep-requests", "0.5",
        "--print", "%(url)s\t%(timestamp)s\t%(upload_date)s",
    ]
    if cookies_file:
        command.extend(["--cookies", str(cookies_file)])
    if not (full_playlist and not is_channel):
        command.extend(["--playlist-end", str(fetch_count)])
    command.extend(["--", expansion_url])
    return command
In plain words

Ask yt-dlp for a plain list of the channel's recent videos with their upload dates, one per line, then throw away the Shorts and anything too new, and keep the first few that survive.

What it does

Input: one channel or playlist URL, how many videos are wanted, the minimum age, and the cookie policy. Output: an ordered list of individual video URLs, or an empty list if both attempts failed. Role: the only place that converts a monitored source into concrete work items.

No --playlist-end at all, so the whole playlist is listed. That mode is only reachable from the "run now" checkbox in the browser page.

Which channel tab gets asked, from the same run: /@examplechannel becomes /@examplechannel/videos; an explicit /streams is preserved; /@examplechannel/shorts is redirected back to /videos; and /channel/UC.../videos is left alone.

Why it asks for six times as many videos

The count in the settings is how many episodes you want, not how many rows YouTube should return. Shorts and videos published in the last day are dropped after the list comes back. If the program asked for exactly two and both were Shorts, it would come away with nothing. Asking for twelve and stopping once two survive costs one listing request either way, because --flat-playlist does not fetch each video's page.

Why a bare channel URL is rewritten to the videos tab

A bare channel address renders differently depending on YouTube's current layout and can mix uploads, Shorts and livestreams. Pinning the request to /videos makes the result predictable. Anyone who genuinely wants livestreams writes /streams in urls.txt, and that choice is respected.

Trap: the retry is not a retry for network trouble

When the first attempt fails, the code tries again exactly once and the only thing it changes is whether cookies are attached. There is no backoff, no second attempt at the same settings, and no attempt number three. A transient network failure simply means the channel is skipped this run and picked up on the next scheduled one. That is a deliberate choice for a program that runs every 48 hours, but it is worth knowing before you go hunting for retry logic that is not there.

05The waiting period — is_old_enough()

A brand-new YouTube video has no SponsorBlock data yet, so downloading it immediately means keeping the sponsor reads. The program therefore waits.

def is_old_enough(timestamp_raw, upload_date, min_channel_video_age_hours) -> bool | None:
    """True if old enough, False if too new, None if age is unknown."""
    if min_channel_video_age_hours <= 0:
        return True

    if _metadata_value_is_present(timestamp_raw):
        try:
            timestamp = int(timestamp_raw)
            age_seconds = datetime.now(timezone.utc).timestamp() - timestamp
            return age_seconds >= min_channel_video_age_hours * 3600
        except ValueError:
            pass

    if _metadata_value_is_present(upload_date):
        try:
            upload_day = datetime.strptime(upload_date, "%Y%m%d").date()
            next_day_start = datetime.combine(
                upload_day + timedelta(days=1), datetime.min.time(), tzinfo=timezone.utc)
            allowed_at = next_day_start + timedelta(hours=min_channel_video_age_hours)
            return datetime.now(timezone.utc) >= allowed_at
        except ValueError:
            return None

    return None
The formula

When yt-dlp gives an exact publication instant $t_{\text{pub}}$ in seconds since 1970, the test is simply

$$t_{\text{now}} - t_{\text{pub}} \ \ge\ 3600\,h_{\min}$$

When only a date YYYYMMDD is available, the exact instant is unknown, so the code assumes the worst case — the very end of that day — and waits from midnight after it:

$$t_{\text{now}} \ \ge\ \text{midnight}(d_{\text{upload}} + 1\ \text{day}) + 3600\,h_{\min}$$

$t_{\text{now}}$ is the current time in seconds, $t_{\text{pub}}$ the publication time in seconds, $h_{\min}$ the setting min_channel_video_age_hours (24 by default), $d_{\text{upload}}$ the upload date, and all times are in Coordinated Universal Time (UTC).

What it does

Input: the raw timestamp text and upload date text from yt-dlp, plus the configured minimum age. Output: True, False, or None. Role: a three-valued answer, not two. None means "I could not tell", and every caller treats that as permission to proceed.

Sample data
in and out — is_old_enough(timestamp, upload_date, 24) 
timestamp 2 hours old                timestamp='1786395218'   upload_date=''           -> False
timestamp 30 hours old               timestamp='1786294418'   upload_date=''           -> True
no timestamp, upload_date today      timestamp='NA'           upload_date='20260810'   -> False
no timestamp, upload_date 2024-01-05 timestamp='NA'           upload_date='20240105'   -> True
both missing                         timestamp='NA'           upload_date='NA'         -> None
garbage upload_date                  timestamp='NA'           upload_date='not-a-date' -> None   <- unknown, not blocked

Checking the second row by hand: the run happened at Unix time 1786402418, so the age is 1786402418 minus 1786294418 = 108000 seconds, which is 30 hours, and 30 is at least 24. True.

Why unknown means allow

yt-dlp writes the literal text NA when a field is unavailable, and its channel listings often omit exact timestamps. If unknown meant "wait", a channel whose listings never carry dates would never download anything at all, and the failure would be silent. Allowing an unknown age risks keeping a sponsor read in one episode. That is the cheaper mistake.

Trap: the date-only path waits longer than you asked

With the default 24 hours and only an upload date available, a video published at 01:00 UTC waits until 00:00 the next day plus 24 hours — that is 47 hours, not 24. This is intentional caution given an unknown publication time, but it means the setting is a floor, not the actual delay.

The one-shot override

Ticking "run now" in the browser, or passing --skip-age-check on the command line, writes the video URL into bypass_age_check_urls.txt. BypassStore.consume() removes the line and reports the match in a single locked read-modify-write, and it does so before the download attempt. So a failed download does not silently keep permission for later runs: the override really is used once.

06Running the downloader — YtDlpClient

src/downloads/ytdlp_client.py is small on purpose. It builds the command, runs it under a time limit, decides whether the cookie retry is warranted, and reports what it saw.

def build_download_command(self, url: str, work_dir: Path, cookies_file: Path | None) -> list[str]:
    """Build one audio-download command with a safe URL separator."""
    command = [
        "yt-dlp",
        "--paths", f"temp:{work_dir}",
        "--extract-audio",
        "--audio-format", "mp3",
        "--audio-quality", "0",
        "--no-mtime",
        "--embed-thumbnail",
        "--add-metadata",
        "--output", str(work_dir / YTDLP_OUTPUT_FILENAME_TEMPLATE),
    ]
    if is_youtube_url(url):
        command.extend(["--sponsorblock-remove", SPONSORBLOCK_CATEGORIES])
    else:
        command.append("--no-playlist")
    if cookies_file is not None:
        command.extend(["--cookies", str(cookies_file)])

    # `--` keeps a user-supplied URL beginning with `-` from becoming an
    # option to yt-dlp.
    command.extend(["--", url])
    return command
In plain words

Build the command, run it, and if it fails, run it once more with the opposite cookie decision. Nothing else.

What it does

Input: a direct media URL and the scratch folder it may write into. Output: a YtDlpResult holding the exit status, the text output, the MP3 files that changed, the before and after file snapshots, and whether one or two attempts happened. Role: the only place that runs the external downloader, which is what makes the download logic testable without a network.

No SponsorBlock and no cookies. Both differences are deliberate: SponsorBlock only has YouTube data, and cookies are private credentials that should never reach an unrelated site.

Why every command ends with a double dash

URLs in urls.txt and in the web form are user input. A URL that begins with a hyphen would otherwise be read by yt-dlp as one of its own options. Putting -- before the URL tells the argument parser that everything after it is a value, never a flag. The command is also passed as a list, never as a shell string, so there is no shell to inject into in the first place.

Why the cookie order is configurable at all

Cookies make YouTube treat the request as a signed-in session. That gets you past "confirm you are not a bot", but a stale or over-used cookie file can also cause failures that a plain anonymous request would not hit. Rather than guessing, the project lets you pick the first choice and always tries the other one once. Both directions are covered by the same two-attempt code path.

07Proving the download worked — file snapshots

This is the most important idea in the project, and the least obvious one.

def snapshot_audio(self, work_dir: Path) -> AudioSnapshot:
    """Capture recursive MP3 modification time and size state."""
    captured_files: dict[Path, tuple[int, int]] = {}
    for audio_file in work_dir.rglob("*.mp3"):
        if not audio_file.is_file():
            continue
        file_stat = audio_file.stat()
        captured_files[audio_file] = (file_stat.st_mtime_ns, file_stat.st_size)
    return AudioSnapshot(files=captured_files)

@staticmethod
def changed_audio_files(before_snapshot, after_snapshot) -> list[Path]:
    """Return MP3 paths created or changed between two snapshots."""
    return sorted(
        audio_file
        for audio_file, after_state in after_snapshot.files.items()
        if before_snapshot.files.get(audio_file) != after_state
    )
In plain words

yt-dlp can finish with a success code and still not have produced an MP3. So the program lists the MP3 files in the scratch folder before it starts and again when it finishes, and only calls the download a success if a file actually appeared or changed.

The formula

Let $B$ be the set of MP3 files in the scratch folder before the attempt and $A$ the set after, and let $s(p)$ be the state of file $p$, meaning the pair (modification time in nanoseconds, size in bytes). A file $p \in A$ counts as changed when

$$p \notin B \quad\text{or}\quad s_A(p) \ne s_B(p)$$

and the attempt counts as a success only when at least one such $p$ exists.

Restricting both sets to this source's own scratch folder matters: a file produced by another source or another process cannot prove that this URL worked.

Sample data
in — two snapshots 
before: {'/w/old.mp3': (1000, 500)}
after : {'/w/old.mp3': (1000, 500),
         '/w/new.mp3': (2000, 900)}
out — changed_audio_files() 
[PosixPath('/w/new.mp3')]

with an unchanged folder:
[]                        <- treated as a failed attempt

An empty result is what triggers the second attempt with the other cookie choice, even when yt-dlp returned exit code zero.

Why size and modification time, not a checksum

These files are tens of megabytes and the comparison happens twice per download. A checksum would read every byte for no gain: the question is not "are these files identical" but "did this run write anything here", and a nanosecond timestamp plus a byte count answers that at the cost of one stat call per file.

Trap: the one-file recovery rule

If nothing changed, the service falls back to _find_recoverable_existing_audio, which accepts the situation only when the scratch folder holds exactly one MP3. That covers the real case it was written for: a previous run downloaded the file but crashed while writing its tags, so this run's yt-dlp says "already downloaded" and changes nothing. It is a guess, though, and the section on limitations explains when the guess can pick the wrong file.

Audiobookshelf reads a podcast episode's publication date from tags inside the audio file, not from the file's timestamp on disk. So after a successful download the project writes its own tags.

command = [

In plain words

Rewrite the file's tags with ffmpeg without re-encoding the audio, then pour the rewritten bytes back into the original file instead of replacing it, so the library scanner keeps seeing the same file.

What it does

Input: an MP3 path, the completion timestamp as text, the source URL, and optionally a readable channel name. Output: nothing on success; a RuntimeError if ffmpeg failed. Role: it decides what Audiobookshelf shows as the episode date and the podcast name, and it leaves a provenance trail so a file on disk can be traced back to its source video.

Sample data — a real ffmpeg run on a real MP3

This is a genuine end-to-end result: ffmpeg wrote the tags and ffprobe read them back. The file grew by 180 bytes, which is the size of the added tag frames; the audio itself was copied, not re-encoded.

Why the bytes are copied back instead of the file being replaced

Audiobookshelf's scanner and file watcher match library files by path and by inode number, the operating system's internal identifier for a file. Renaming a temporary file over the original would give the path a brand new inode, and the library could treat it as a delete followed by an add — losing the listen position. Copying the bytes into the existing file keeps the inode, so nothing downstream notices.

Why the date is the download time, not the upload time

You want your podcast app to show new arrivals in the order you received them. A channel backfilling a five-year-old talk would otherwise bury it. The same tag is what the retention rule later reads to decide the file's age, so "keep for 30 days" means 30 days since you got it.

Trap: the temporary filename must not end in .mp3

The temporary file is named .<original name>.download-date.tmp. If it ended in .mp3 it would appear in the next snapshot_audio call, be counted as a changed audio file, and be published into the library as a duplicate episode. The leading dot also hides it from most file browsers.

def _sanitize_download_folder_name(self, raw_name: str) -> str:

Why there are two folders, scratch and library

intermediate_dir receives the partial downloads, the thumbnail, the intermediate audio stream and the tagging temporary file. Only a finished, tagged MP3 is moved into output_dir. Audiobookshelf watches output_dir, so it never sees a half-written file and never tries to import a fragment. If the two paths are configured to be the same folder, the code detects that and falls back to deleting non-MP3 leftovers in place instead of moving anything.

Why failure deletes the whole scratch folder

Every failure path calls _finalize_intermediate_cleanup(work_dir), which removes the source's scratch folder outright. A failed item is not written to the history file, so the next run tries it again from scratch. Leaving fragments behind would make the next run's before-and-after snapshot ambiguous.

The two locks around a download

Channel and playlist items are wrapped in archive_store.locked_download_claim(), a lock on a small separate file. The history file itself is only locked for the brief read and the brief append. That is the point: a download can take an hour, and holding the history file for an hour would stall the browser page every time it checks for duplicates. One-off videos use a different lock, .direct-download.lock inside the scratch folder, because all of them share the singles workspace.

Trap: the history file is only written after success

downloaded_urls.txt gains a line when the MP3 has been tagged and published, never before. That is what makes a failed download automatically retryable and what makes a timeout so expensive: a video that always exceeds download_timeout_seconds is retried on every single run, forever, because it is never recorded as done.

10Deleting old episodes — retention

In plain words

Before a full run starts, look through the folders belonging to monitored YouTube channels, read the date the program wrote inside each MP3, and delete the ones older than the retention window — also removing that video from the history file so it could be fetched again later.

The formula

An MP3 at path $p$ is deleted when all four conditions hold:

$$p \in D_{\text{channel}}, \quad d(p) \ \text{is readable}, \quad u(p) \ \text{is readable}, \quad d(p) < t_{\text{now}} - R$$

$D_{\text{channel}}$ is the set of output folders belonging to YouTube channels currently listed in urls.txt; $d(p)$ is the download date read back out of the file's own date tag; $u(p)$ is the source URL read out of its comment tag; $t_{\text{now}}$ is the current Toronto time; and $R$ is retention_days, 30 by default.

Why so many conditions have to line up

Each one blocks a different way of deleting the wrong thing. Restricting to current channel folders keeps playlists and one-off downloads safe. Requiring a readable date means a file the program did not tag — something you copied in by hand — is never touched. Requiring the source URL means the program can also remove the matching line from downloaded_urls.txt; without it, the file would vanish from disk while still being remembered as downloaded forever, so it could never come back. Every skipped file is logged with the reason.

Trap: retention runs before the history check, not after

In download_all, cleanup happens first. If it ran afterwards, this run would skip a video because it was still in the history file, and only then delete the file and its history line — leaving a gap until the next run. Doing it first means an expired episode becomes eligible again in the same pass.

How sign-in works

What it does

Input: a username and password typed into the form, plus a one-time token. Output: a random session identifier stored in a cookie and in .ui_sessions.json. Role: the only gate in front of every queue edit.

Passwords are never stored. src/passwords.py derives a key with PBKDF2-HMAC-SHA256 — Password-Based Key Derivation Function 2, the standard slow-hashing construction — using 600,000 iterations and a 16-byte random salt, and stores the result as pbkdf2_sha256$iterations$salt$hash. On every start-up, src/credentials.py reads the plain passwords from .env, checks them against the stored hashes, and only re-hashes when something changed.

Sample data
in and out — hash_password() then verify_password() 
hash_password("correct horse battery staple")
  -> 'pbkdf2_sha256$600000$_WfqIBCT9slw60mLrRyiUw$mNHi8im1JustYipg8g-gR7D2eLfJvg4vIFe9kZp9EKg'

verify_password("correct horse battery staple", stored)  -> True
verify_password("wrong", stored)                          -> False
verify_password("x", "not-a-hash")                        -> False

The stored value carries its own iteration count and salt, so the check reads them back out of the string. verify_password refuses any iteration count outside 100,000 to 1,000,000, which stops a tampered file from demanding unbounded processor time during a sign-in attempt.

Why a wrong username costs the same time as a wrong password

If the code skipped hashing when no account name matched, a failed sign-in would return instantly for an unknown name and slowly for a known one — enough of a timing difference to let an attacker enumerate valid account names. So when no name matches, the code hashes the submitted password against the first account's stored hash as a decoy, throws the result away, and reports the same failure. The name comparison itself uses secrets.compare_digest, which takes the same time regardless of where the strings first differ.

The ban rule

Five failed attempts within a ten-minute rolling window from the same client address set a fifteen-minute ban, recorded in .login_state.json. A failure that arrives after the window has elapsed starts the count fresh. The ban is checked before the password is ever hashed, so a banned address cannot be used to burn processor time.

Trap: every form carries a token, and the login form's token is single-use

Cross-Site Request Forgery is the attack where another website makes your browser submit a form to this one while you are signed in. Each page therefore embeds a random token that the server also remembers, and each form submission must present it. The sign-in form's token is popped from the server's map the moment it is used, and expires after ten minutes, so a captured form cannot be replayed.

Why /logs answers 401 instead of redirecting

The queue page polls /logs from JavaScript every fifteen seconds. A redirect would be followed silently by fetch, which would then receive the sign-in page's HTML and render it inside the log box as if it were log lines. Returning the status code 401, meaning "not authenticated", lets the script recognise an expired session for what it is.

Response headers on every page

auth.py sets a Content Security Policy of default-src 'none' with a per-request random nonce for the one inline script, plus frame-ancestors 'none', X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: same-origin and Cache-Control: no-store. In plain terms: the page may not load anything from another site, may not be embedded in another site's frame, and may not be cached.

12The scheduler — start.py and trigger.py

Inside Docker, one process serves the web page and runs the schedule. start.py keeps the web server in the main thread and puts the scheduler in a background thread.

In plain words

Every 48 hours: update yt-dlp, wait five minutes, then run the whole queue by launching the command-line program as a separate process. If someone adds a URL through the browser in the meantime, wake up early and handle just that one URL.

What it does

Input: the environment variables DOWNLOAD_INTERVAL_HOURS and YT_DLP_AUTO_UPDATE, plus wake-up requests from the browser. Output: child processes running python -m src.cli, with no arguments for a full run, or with --download-single-url or --download-full-playlist for an immediate one. Role: the only thing that decides when downloads happen.

Why the downloader runs as a separate process

A crash or a memory leak inside yt-dlp handling takes down a short-lived child process, not the web server you use to fix the problem. The child also gets a clean logging setup and a clean working directory every time. The cost is that the two processes share state only through locked files — which is exactly why src/state/ exists.

Why the browser hands over the URL, not just a wake-up signal

trigger.py keeps two lists guarded by a lock, one for single videos and one for full playlists. If the browser only rang a bell, the scheduler would have to process the entire queue, expanding every channel, just because you pasted one link. Passing the exact URL keeps an immediate run to one item.

Trap: adding a channel does not start anything

Only direct videos and explicitly ticked playlists trigger an immediate run. A newly added channel waits for the next scheduled cycle, which can be up to 48 hours away. This is intentional — expanding a channel is the expensive path — but it surprises people, and the browser page gives no visible hint that nothing is about to happen.

One defect found and fixed — src/media/youtube.py

The bug. normalize_youtube_url built the video identifier from parsed.path.lstrip("/"), which removes a leading slash but not a trailing one. FLimitations, stated honestly

Retagging can destroy an MP3 if the disk fills up

AudioMetadataWriter opens the finished MP3 for writing, which truncates it to zero bytes, and then copies the retagged bytes in from a temporary file. If that copy fails part way — a full disk is the realistic case for a downloader — the original is already gone, and the finally block deletes the temporary file that held the only complete copy. The caller then preserves the now-truncated MP3 for a later retry, and a later run can adopt it through the one-file recovery rule and publish it. Keeping the inode stable for Audiobookshelf and never truncating the original are genuinely in tension; resolving it needs a decision about which one wins, so it is documented here rather than patched.

The one-file recovery rule can adopt the wrong MP3

_find_recoverable_existing_audio accepts any single MP3 sitting in the scratch folder when a run changed nothing. Suppose video A's tagging failed, leaving A's MP3 in the folder, and the run then reaches video B, whose yt-dlp attempt exits 0 without producing a file. The snapshots are identical and exactly one MP3 is present, so A's audio is tagged with B's source URL, published, and B is recorded as downloaded. A tighter rule would require the filename to contain the video identifier that yt-dlp puts in square brackets, but that would not work for non-YouTube sources, so it was left as is.

Channel folder names are not stable

For a /channel/UC... source, the readable folder name comes from a live yt-dlp lookup performed on every run. There is no cache. A single network failure sends that run's downloads into a folder named after the raw identifier, and retention cleanup will then only ever look at one of the two folders. Sources written as /@handle are not affected, because the name comes from the URL itself.

Everything depends on parsing yt-dlp's output

Channel expansion reads tab-separated lines printed by yt-dlp --print, and the age gate reads the literal string NA as "missing". Both are conventions of a tool that changes often to keep up with YouTube. An upstream change to either would not raise an exception; it would quietly produce zero videos, which looks exactly like a channel that has not posted anything.

One shared account list, one process

Sign-in is a small number of shared accounts from .env, not per-user identity, and the active-session map lives in the memory of a single process. Running the web server with more than one worker would break sign-in outright, because each worker would keep its own map. The README is honest that this is a personal tool, not a multi-user service.

The shipped settings trust proxy headers

trust_x_forwarded_for = true ships in config.ini, while the code's own default is false. That is coherent with the supplied Docker Compose file, which binds the port to 127.0.0.1 behind a reverse proxy. But anyone who exposes the port directly and keeps the shipped settings lets a client claim any address it likes in an X-Forwarded-For header — and the sign-in ban is recorded per address, so the ban becomes trivial to evade. The setting is documented in both the file and the README; it is still the sharpest edge in the configuration.

The detailed log rotates, but from more than one process

download.log uses a rotating handler with a five-megabyte limit and three backups. Each downloader run is its own process. If two ever overlap — a manual command-line run while the scheduler is working — a rollover in one process can drop entries written by the other. Nothing is lost that matters to the download itself, but the log is not a perfect record under concurrency.
