# Podcast Downloader: strategic review, 2026-09-05

The downloader already has the machinery needed for its stated purpose. The next useful work is to establish that selected episodes keep reaching Audiobookshelf, and that an interruption reaches you without requiring you to watch logs. Adding more ways to submit or organize content would contribute less than making the existing delivery path trustworthy.

**Scope and evidence.** This review reads the current working files, including pre-existing source changes, rather than assuming the committed revision or documentation describes today's implementation. Coverage includes every application module under `src/`, both root Python entry points, all scripts, extension JavaScript and assets' manifests, all 24 test modules, configuration and deployment files, every developer guide, all narrative documentation, and the English/French blog and its generator/data. `AGENTS.md` was revisited after reading the implementation and is the authority for intent. Generated extension packages and image assets were inventoried; the generated HTML explanation was sampled and the dependency lock's package inventory inspected. Their contents are not evidence of current production behavior. Credentials, installed dependencies, caches, and deployed media were not inspected.

No application, tests, downloads, deployment, network requests, or live service checks were run. Test references below describe saved test coverage, not results obtained in this review. This report is the only file created; the existing Fable review and other working changes are preserved.

**1. What the project actually does today**

`main.py` delegates to `src/cli.py`; `start.py` combines the web application with the scheduler. The command-line interface can enqueue links, run the queue, process one direct video, process one saved source, or request an entire playlist. Starting `src.api:app` alone exposes the web application but does not start the scheduler. Docker uses the combined entry point.

The web forms and authenticated application programming interface (API) share queue decisions in `src/web/queue_actions.py`. They normalize equivalent YouTube video links, reject duplicates, and wake immediate work for direct videos. Channel subscriptions remain queued. The browser extensions submit a URL through the same API; their success badge means submission was accepted or already handled, not that an episode has reached the listening app. Their connection check uses `/api/ping`, which checks the web service's availability.

Source selection is deliberately bounded (`src/media/youtube.py`, `src/downloads/service.py`). The shipped configuration takes two eligible videos per channel, examining up to twelve candidates and skipping Shorts. Known upload times normally impose a 24-hour wait. Unknown upload age is permitted. Bare channel links select the videos tab; explicit streams links retain that tab. Regular playlist expansion takes the first configured number of entries in playlist order, which is not necessarily newest-first. Normal playlist expansion does not apply the channel age filter; a targeted saved-playlist run checks age separately, while the explicit full-playlist action selects every entry. These distinctions determine which listening material actually arrives.

`src/downloads/ytdlp_client.py` delegates extraction and MP3 conversion to `yt-dlp` and FFmpeg. YouTube requests ask SponsorBlock to remove its `sponsor` and `selfpromo` categories. The application waits for upload age rather than establishing that sponsor segments exist. Other supported sites use direct downloads without SponsorBlock processing; Rumble gets a specific browser-impersonation option. YouTube can try cookies and then no cookies, or the reverse, with a one-hour default timeout per download attempt. Future premieres and livestreams are deferred without failure notifications.

Publication has substantive safeguards. The client compares MP3 size and modification time before and after work in the active source scratch folder. The service requires a successful final command and new or changed audio, with a narrow single-existing-file recovery path for a previous metadata failure. `src/downloads/audio_metadata.py` writes the completion date, source URL, and available channel identity. Only after tagging and moving audio into the final library does the workflow remove pending work and record expanded videos in the archive. Separate claim locks coordinate slow downloads while archive reads use shorter locks (`src/state/`). This is local filesystem coordination for one host, not a distributed queue.

The final output has channel/playlist folders and `singles/`. Retention reads the embedded completion date, not the original release date, and deletes sufficiently old files only in currently monitored YouTube channel folders. It requires both date and source-URL tags and otherwise keeps the file. Deletion also removes the corresponding archive entry, allowing that video to become eligible again. Playlists, singles, and folders outside current channel retention coverage do not have this automatic space limit.

Scheduling is based on Toronto calendar time, by default at 06:00 every other day, with startup catch-up for a missed whole-queue pass (`src/schedule.py`, `start.py`). The deployment keeps configuration and state in mounted storage, repairs ownership, and runs the application as the configured user. It installs and can automatically update `yt-dlp` separately from the Python dependency lock. Web authentication supports three shared-privilege accounts, saved sessions, failed-login bans, form protection, and private cookie uploads. Extension packaging and deployment scripts are already substantial supporting infrastructure.

Operational visibility is also already built. `src/run_report.py` and `src/notifications/apprise_client.py` send download failures, an aggregate alert when all monitored listings are empty, and cookie-expiry warnings through Apprise, a notification gateway. The scheduler reports missed runs after restart and unsuccessful downloader processes. The web activity feed groups recent events and exposes problem filtering. `/api/health` returns an overdue status when a whole-queue run is sufficiently late, whereas `/api/ping` only proves that the web process answers. Successful runs intentionally send no routine success message.

**2. The gap against the ultimate goal**

`AGENTS.md` defines the outcome as a reliable, clean, sponsor-free Audiobookshelf library with little ongoing attention. It explicitly calls the build phase complete. The source supports that assessment at the component level; the remaining gap is narrower than a missing downloader or missing alert system.

| Goal component | Current position | Remaining gap |
|---|---|---|
| Submit and process selected sources | Built: command line, web, API, browser clients, scheduled and manual work | Decide whether bounded recent selection is sufficient for the actual listening habit |
| Publish tagged MP3 files safely | Built: scratch isolation, artifact checks, metadata, publication, archive coordination | No application acknowledgment that Audiobookshelf indexed and played the intended episode |
| Notice operational failure | Partly complete: several alerts, activity feed, catch-up, authenticated health route | Independent monitoring and actual recipient delivery are deployment facts not demonstrated here; partial source failure is less visible |
| Stay sponsor-free | Best-effort segment removal is built | No recorded distinction between no sponsors and no available annotations; waiting 24 hours is a heuristic |
| Recover with little intervention | Cookie upload, alternate authentication mode, updates and diagnostics exist | No demonstrated recovery time, automatic credential renewal, or maintained proof that current upstream extraction works |
| Keep storage and identity predictable | Channel retention and source tags are built | Retention excludes other library areas; one explicit metadata invariant disagrees with current implementation |

That last disagreement deserves an explicit decision before more metadata work. `AGENTS.md` requires preserving the MP3 inode, the filesystem identity behind its path. Current `audio_metadata.py` stages output and atomically replaces the original path, thereby changing its inode; current tests and `docs/operations.md` describe that behavior. The blog still describes preserving the inode. This is an unresolved contract between the declared invariant and the selected publication behavior, not evidence from this review that Audiobookshelf is currently breaking. Preserve the existing implementation during this review; later establish which identity properties Audiobookshelf actually requires and reconcile the authoritative intent with that evidence.

Not implemented in application code are persistent per-source delivery history, a bounded-duration running-state watchdog, and confirmation from the listening application. A sophisticated monitoring platform is unnecessary; these are questions that a small amount of operational evidence could answer.

**3. Concrete next steps, in priority order**

Effort estimates assume one person familiar with the project. They describe future work, not work performed here.

1. **Prove the monitoring already provided.** Confirm the deployed Apprise settings reach the intended recipient, and establish an external check of `/api/health` that remains capable of alerting when this service stops. Record one received test notification and one detected service interruption, then observe several scheduled cycles. This comes first because existing capability can reduce unattended failure immediately, without new product code. It serves the low-attention goal and establishes the baseline for deciding whether more alerts help. **Size:** half to one day of setup and evidence gathering, plus roughly a week of elapsed observation. **Dependency:** access to the actual deployment; the repository cannot establish whether this is already configured.

2. **Write a small operational acceptance contract.** Choose what counts as expected delivery, acceptable delay, acceptable sponsor coverage, and tolerable operator attention. Settle whether channels mean “the latest few available episodes” or “every episode since I last checked,” and distinguish the former from a backlog promise. Include the metadata identity decision above, using one representative Audiobookshelf import/playback check. This precedes new instrumentation because an alert cannot distinguish normal inactivity from a missed promise until that promise exists. **Size:** half to one day. **Dependency:** the owner's actual listening expectations; sensible defaults can be proposed without designing a larger product.

3. **Make silence explainable per source.** Retain a compact last-outcome record: listing failed, nothing eligible, already archived, newly published, or download failed, with time and repeated-failure count. Escalate sustained exceptions and stalled progress according to step 2. Report fresh publications separately from existing “successful” counts, which can include archive skips and Shorts skips. Keep messages bounded and consolidated; a low-frequency digest is worthwhile only if it answers a useful question better than exception alerts. This is the smallest meaningful capability gap after existing monitoring is operational. **Size:** two to four days including behavioral verification. **Dependency:** acceptance thresholds and step 1's working notification path.

4. **Rehearse upstream recovery once and retain the minimum runbook.** Demonstrate the path from a representative extraction failure to a playable episode: inspect preserved attempt evidence, distinguish cookie problems from extraction/client requirements, refresh credentials or change the relevant setting, and verify the final library result. Record the last working extractor version and a practical way to return to it after an update. A proof-of-origin token is an upstream access credential; a dedicated provider should be considered only when observed failures make it necessary. This follows detection because recovery work should answer a measured failure, not speculative platform changes. **Size:** one to two days initially; any new external integration requires a separate estimate.

5. **Close the storage and restore policy.** Choose whether singles/playlists are permanent, what happens to unsubscribed folders, and whether deletion should make episodes downloadable again. Demonstrate restoration of source selections, configuration, archive and retained media from private storage; set a simple disk-space threshold covering both scratch and final directories. This protects unattended operation as the library accumulates content. It comes after delivery visibility because storage policy depends on what the library is meant to retain. **Size:** half to one day for decisions and one restore exercise; implementation only where the exercise establishes a gap.

6. **Consider chapters only after the above is quiet.** If actual listening exposes navigation friction, try chapter markers on one representative episode while preserving the agreed date, source and identity contract. This is directly useful but does not unblock reliable delivery. **Size:** roughly one to three days for a focused trial, contingent on available chapter data and Audiobookshelf behavior. Skip it if it creates recurring maintenance.

**4. Decisions and simpler paths that may be easy to miss**

The age gate, candidate limit and polling interval collectively define coverage. With two selected videos per channel, a busy source can publish more eligible videos than one pass takes. An outage can leave earlier releases outside the bounded window. That can be entirely acceptable for a recent listening shelf; it is incompatible with silently assuming complete subscription delivery. Decide coverage before increasing counts or introducing backlog storage.

“Sponsor-free” has two different meanings: requested removal of known segments, or verified absence of sponsorship in the final audio. The implementation provides the former. An unknown upload date also bypasses the normal waiting heuristic. A cheap policy decision now is whether uncertain coverage should delay publication, remain visible as uncertainty, or be accepted. Avoid promising certainty that neither the file check nor SponsorBlock annotations establish.

The archive is a record used to suppress downloads, not a permanent listening history. Retention removes entries from it. This couples freeing space to future selection: an old episode still near the top of a quiet channel can return. The existing retention test explicitly expects this possibility. A rolling shelf and a permanent “already consumed” history are different products; choose the simpler one that matches actual use.

Readable source folders are convenient, but their names can depend on remote metadata. Think through how a renamed source should remain recognizable and eligible for retention before accumulating years of files. Likewise, a stable filename does not imply a stable inode. A brief written identity rule is cheaper than repeated uncertainty whenever metadata gains a new field.

Keep plain-file state and one deployment. There is no goal-driven reason to add a database, multiple workers or replicas merely because the source has substantial code. Similarly, the existing web and browser submission routes cover the ordinary workflow; another intake client is unlikely to save as much attention as a reliable exception message.

**5. Improvement directions beyond the current plan**

The best direction is a personal appliance with a measurable attention budget. During a two-week observation period, record expected versus delivered episodes, actionable interruptions and minutes spent intervening. Use those observations to choose one next investment, then stop adding machinery once the listening promise is met. This is an operating experiment, not a permanent analytics product.

After reliable delivery, metadata quality and usable chapters are the strongest expansion candidates because they improve the listening experience inside the existing pipeline. Keep the trial small and reject it if its upkeep exceeds its benefit.

Transcripts, semantic search, research workflows, public Really Simple Syndication (RSS) distribution, additional account models, and broader provider integrations may be interesting projects. They do not serve this repository's explicit goal sufficiently to recommend here. Audiobookshelf is already the distribution boundary.

**6. What could quietly steer the project away from its goal**

- **Completed runs can mask failed delivery.** `run_state.json` records when a whole-queue process finished, not its per-source outcome. A running flag stays healthy without a time ceiling. Saved tests make these distinctions explicit. Schedule monitoring therefore needs an agreed progress interpretation before it can stand for delivery health.
- **Partial source failure can remain ordinary-looking.** The all-empty alert helps when everything fails; one failing channel among working channels remains an activity-log event. Repeated failure must be distinguished from a genuinely quiet source without making every empty listing noisy.
- **The alert path can share the outage.** An external monitor on the same failed host, or Apprise without working downstream delivery, offers limited independence. Notification submission has a timeout but no durable retry queue. Prove receipt; add retry machinery only if actual delivery evidence warrants it.
- **Updates and credentials remain external dependencies.** Automatic extractor updates reduce manual maintenance and also change behavior outside `uv.lock`. Cookie expiry is only a bound recorded in the file, not proof the sign-in remains accepted. Avoid treating either successful update output or a future expiry date as successful extraction.
- **Large manual playlists can consume the attention budget indirectly.** Every-entry selection combined with sequential, potentially lengthy attempts can delay other work. Set expectations about acceptable queue delay before pursuing concurrency, which would undermine the intentionally simple deployment.
- **Storage can become the next silent limit.** Channel-only retention, retained uncertain metadata, permanent singles and scratch processing have different growth patterns. The final MP3 existing does not prove it was indexed, playable, or heard without sponsorship. One periodic real listening-path check is more informative than adding reassuring counters.

**TL;DR**

- **Request** — Assess the entire project against its stated goal and recommend strategic next steps without changing code.
- **Answer** — The product is built; prioritize proven external monitoring, a clear delivery promise and compact per-source outcomes, then rehearse recovery and settle retention/metadata contracts before adding listening features.
